# 03: macOS 正常网络下的双向同步

**What to build:** 用户在 macOS 显式开启双向模式后，本地同步文本变化会经 ntfy 到达其他 peer；远端写入不会再次上传，自身回送不会覆盖本地新内容。先完成可实际演示的正常网络闭环，后续票据再增加完整失败重试和积压策略。

**Blocked by:** 02 — 接收新版协议与普通 ntfy 文本。

**Status:** ready-for-agent

**Execution:** 已实现 macOS 原生 helper 与共享协调器；macOS/KDE 的真实同步及官方 ntfy 三 peer 测试通过。完整验收范围见[验证记录](../../../docs/clipboard-sync-validation.md)。

本票必须完成基本状态正确性，不能将稳定快照、串行写入登记或防同值回环推迟到重试任务。范围不包含其他平台监听、服务器历史重放、事件历史去重或来源过滤。

- [ ] 在目标 macOS 上验证原生读取、changeCount 变化检测和写入能力，记录 SDK/运行系统与依赖版本、线程及访问权限约束；不可用时明确报告，不静默绕过权限。
- [ ] 双向模式默认按 250 ms 检查变化，可配置；默认 receive 模式不启动后台监听。启动首次成功读取仅建立基线，不上传旧内容。
- [ ] 本地观察、比较、发布及远端写入均以同步文本为准，计算其 UTF-8 SHA-256；不重写用户刚复制的原始文本，不维护历史 hash 或系统私有标记。
- [ ] 同步文本 hash 变化时先更新观察状态，再登记发布；连续同值或仅改变末尾 CR/LF 不发布，X→Y→X 的后一个 X 不被历史过滤。
- [ ] 空文本正常发布；系统清空和非文本仅重置观察状态，使以后再次复制先前文本仍能发布；读取失败不冒充清空。多格式内容只取可用文本表示。
- [ ] 使用带保留 tag 的 v1 封装经 HTTP 发布到同一 topic，复用服务器、topic、TOKEN 和对应 HTTP/TLS scheme；按实际序列化 UTF-8 正文含转义开销校验上限，不自动变成附件。
- [ ] 远端先过滤自身 origin，再读取当前实际剪切板；先处理发现的未观察本地变化，同值不写入。写入结果与自身完成登记串行协调，成功才登记预期 hash，不把外部抢写结果记成自身写入。
- [ ] 积压通知重新读取或核对快照新鲜度，不将旧快照重新上传；网络等待不阻塞观察和状态协调。为后续平台建立明确的观察、读取、写入、完成和终止边界。
- [ ] 监听、HTTP 发布、WebSocket 接收生命周期分离；重连不重置 origin 或本地状态，WebSocket 不通不妨碍仍可成功的 HTTP 发布；不请求服务器历史。后台失败能够被监督和报告。
- [ ] 正常路径已具备有界通道、单个在途发布和明确失败报告，不使用无界积压或假成功。完整 FIFO 容量/寿命、网络重试及写入重试由 04/05 交付，不在本票宣称这些行为已完成。
- [ ] 在可控的官方 ntfy 实例上使用合成文本验证三个订阅者均可接收、tag 转发及封装保真；记录版本和限制。至少验证本机真实复制→发布→另一接收端，以及外部发布→本机真实剪切板。
- [ ] 覆盖启动基线、空文本、非文本转换、尾部换行、自身回送先于 HTTP 响应、延迟自身回送及写入通知时序；无重试时复制一次的发布计数保持为 1。通过受影响范围的格式、构建/类型检查、lint、测试及 macOS smoke test。
