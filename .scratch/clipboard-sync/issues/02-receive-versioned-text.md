# 02: 接收新版协议与普通 ntfy 文本

**What to build:** 用户升级后，普通 ntfy 文本和新版 peer 的协议消息都能正确写入剪切板；各平台统一得到去掉尾部全部连续 CR/LF 的同步文本，空字符串仍可同步，损坏的封装不会被当成用户正文粘贴。

**Blocked by:** 01 — 整理现有接收链路，明确写入结果。

**Status:** ready-for-agent

**Execution:** 已实现版本化协议、兼容文本、统一规范化、origin 和大小/配置验证；见[验证记录](../../../docs/clipboard-sync-validation.md)。

遵循已确认规格及“用版本化应用消息传输剪切板文本”ADR。本票交付完整接收路径，不实现本地监听或 HTTP 发布。

- [ ] 仅将配置 topic 的 message 事件送入接收处理；心跳、连接事件及其他 topic 不写剪切板。
- [ ] 有保留 tag ntfy2clip 的消息按 v1 应用封装解码，验证版本、origin 和 text；损坏 JSON、非法字段、未知版本显式报告并跳过，不降级复制封装正文。
- [ ] 没有保留 tag 的普通文本保持兼容，即使看起来像 JSON 也不解包；仅图片/附件通知不下载，也不将自动附件说明写成同步正文。
- [ ] 所有写入路径使用同一同步文本规则：只移除末尾全部连续 CR/LF，保留开头及中间换行、空格和 Tab；明确此规则不保证多行文本在所有终端中粘贴都不会执行。
- [ ] 空字符串及仅由 CR/LF 构成的输入能产生空文本；协议承载保留其他空白，不依赖 ntfy 普通正文保真。
- [ ] 为本次进程生成随机 origin，网络重连不改变；自身 origin 的协议消息不写回，即使本机已有不同内容。origin 不替代 ntfy 认证。
- [ ] 默认模式仍为 receive；非法新增配置显式报错。在监听能力尚不可用时明确报告能力限制，不假装双向同步已开启，也不破坏可用的仅接收路径。
- [ ] 实施默认 4096 字节的可配置消息大小边界和有界解码；超限明确拒绝，不截断、不走附件，不把服务端默认值当成所有自建实例的固定值。
- [ ] 用接收入口到真实或项目自有假剪切板的集成测试覆盖合法封装、普通文本、非目标消息、Unicode、空文本、尾部规则、坏输入及自身回送；补充升级兼容说明。
- [ ] 通过受影响范围的格式、构建/类型检查、lint、测试和接收 smoke test；不得把仅单元测试通过表述为全部平台验证通过。
