# 剪切板监听与文本同步

状态：实现已落地，发布验收未全部完成；见[验证记录](../../docs/clipboard-sync-validation.md)。已按用户后续指令取消 Windows/WSL 支持；未执行的真实矩阵不以模拟测试替代。

本文件是已确认行为和默认值的唯一规格；术语见 [CONTEXT.md](../../CONTEXT.md)，调查依据见 [调研记录](../../docs/clipboard-sync-plan.md)，协议取舍见 [ADR-0001](../../docs/adr/0001-versioned-text-sync.md)。

## 1. 目标与范围

为单人多设备使用的 n2c 增加本地剪切板监听与主动发布，保留已有 ntfy WebSocket 接收及剪切板写入能力。用户使用官方二进制部署的自建 ntfy；它按 topic 广播，不是竞争消费队列。

尽力完成两个方向的交付：将已观察到的同步文本变化发布到服务端，将已经收到的文本写入本机剪切板。防止同值内容在本程序和远程桌面之间持续重复传播，允许有界失败重试和偶发重复通知。

首版范围：

- 文本，包括空字符串；不增加图片、文件、附件下载或消息分片。
- 当前内容 hash + 网络 origin；不保存历史 hash、不写系统私有标记、不要求 event_id。
- macOS、Xorg，以及具备 data-control 能力的 Wayland；重点验证 KDE Wayland。
- Windows/WSL 不支持；WSL 即使具有 WSLg 显示变量也明确拒绝，不误选 Linux selection。原 tickets 06/07 取消。
- GNOME Wayland 首版不做自动上传，不开发 Shell 扩展；保留当前可用的接收路径并明确报告限制。
- 不增加服务器历史重放、跨进程任务恢复、全局排序或恰好一次交付协议。

服务端版本、消息大小及速率配置尚未获取，实施时核对，不套用 ntfy.sh 的托管额度。

## 2. 文本语义

定义 `N(text)`：仅移除末尾全部连续的 CR（U+000D）和 LF（U+000A）。所有开头空白、中间换行、空格和 Tab 保留；不调用通用 trim，不做 Unicode 或中间换行归一化。

| 原始文本 | 同步文本 N(text) |
| --- | --- |
| `abc\r\n\n` | `abc` |
| `a\nb\n` | `a\nb` |
| ` abc \n` | ` abc ` |
| `abc\n ` | `abc\n ` |
| `\r\n` | 空字符串 |
| 空字符串 | 空字符串 |

所有平台一致应用此规则：本地观察后的比较与发布、远端文本的比较与写入都使用同步文本。用同步文本的 UTF-8 字节计算 SHA-256；hash 只在客户端维护，不信任网络声明的 hash。

仅因本地复制而观察到内容时，不重写该设备的原始剪切板。原始文本从 `abc` 变为 `abc\n` 不产生新的同步文本变化；`X → Y → X` 中后一次 X 仍应同步，不能因为历史上出现过 X 而过滤。

空文本、系统清空、非文本、读取失败是不同状态：

- 空文本是合法同步文本，正常发布和写入。
- 系统清空或仅有非文本格式时，不发布清空命令，但将本地状态更新为没有当前文本 hash；以后再次复制先前文本仍能触发发布。
- 同时存在富文本/图片与可用文本表示时，只处理文本表示，不传输其他格式。
- 读取失败不等于清空；报告错误并保留最后一个有效观察状态。

原有 Xorg 的 `xclip -r` 体现了删除尾部换行的意图，应保留这一行为。新规则比它更明确：在共享文本处理层移除全部尾部 CR/LF，送到写入命令时已无尾部换行，不能只依赖某个平台的命令参数。

这是有意的文本变换，不承诺逐字节保留末尾换行。删除末尾换行也不保证多行文本在任意终端粘贴时绝不执行。

## 3. 模式、启动和平台能力

- `SYNC_MODE=receive` 为默认，仅接收；无需安装新增监听组件即可保留原有可用接收能力。
- `SYNC_MODE=bidirectional` 开启本地监听与主动发布。
- 双向模式启动时读取当前剪切板建立基线，不主动发送启动前内容。读取失败则报告并继续尝试，首次成功读取仍建立基线，不冒充启动后的复制。
- WebSocket 重连不重置 origin、当前观察状态或发送队列。监听、HTTP 发布和 WebSocket 接收具有独立生命周期；订阅断线不能阻止仍可成功的 HTTP 发布。
- origin 为每次进程启动生成的随机 UUID，进程内和网络重连时不变，不跨进程持久化。origin 不是认证身份，权限仍由 ntfy 控制。
- 双向模式所需的监听能力不可用时，明确报告请求模式、有效模式和原因，保留可用的仅接收路径。不能静默降级并宣称双向同步正常。
- 不读服务器历史、不使用 since；进程重启不恢复旧队列。

仅接收路径仍进行协议解码和 N(text) 处理，但不要求后台监听能力。能读取当前剪切板时可避免同值写入；不能读取的仅接收后端沿用写入能力并显式报告读能力限制，不能凭上次写入的 hash 假定系统内容未变。它不发布本地内容。

## 4. ntfy 消息协议

所有同步 peer 一起升级；不保证旧版二进制接收新版同步消息时仍得到原文。新版继续接收普通 ntfy 文本。

应用协议 v1：

- HTTP POST 到 `/{topic}`，正文作为普通 ntfy 消息承载，不是向服务器根路径提交 ntfy JSON 发布请求。
- 使用 ntfy 支持的 `X-Tags: ntfy2clip` 标识本应用协议。
- HTTP 正文为 UTF-8 JSON 字符串，内容类型可用 `text/plain; charset=utf-8`。

```json
{"v":1,"origin":"<本次运行的 UUID>","text":"<同步文本>"}
```

空字符串通过 `"text":""` 表示。正文封装保护开头、中间及非 CR/LF 尾部空白不被 ntfy 的普通正文 TrimSpace 改写；尾部 CR/LF 的移除是本项目明确的规则。

接收规则：

1. 只处理配置 topic 的 `event=message`；连接事件、心跳不进入同步状态。
2. 含保留 tag `ntfy2clip` 的消息按应用协议解码；版本不支持、字段缺失、origin 非法或正文类型错误则报告并跳过，不能把损坏的封装当成用户文本复制。
3. 不含该 tag 的普通文本直接作为兼容输入，经 N(text) 后处理；不能仅因为文本看起来像 JSON 就解包。
4. 自身 origin 的协议消息直接忽略，即使本地已经变成不同文本。
5. 不下载附件；含 attachment 的通知不当作图片/文件内容同步，也不把自动生成的附件说明写成同步正文，记录为不支持的消息。
6. 对实际序列化后的 UTF-8 消息正文检查 `MAX_MESSAGE_BYTES`，包含封装和转义开销；超限明确报告，不能截断或自动转成附件。接收端同样做有界解码和文本大小检查。

复用 SERVER、TOPIC、TOKEN，`wss → https`、`ws → http`。TOKEN 必须有相应读写权限。保留 SCHEME、TIMEOUT、RUST_LOG、DEV 的已有用途；TIMEOUT 仍是连接无流量超时，不改作发布重试预算。

## 5. 状态协调与防同值回环

一个状态管理流程协调已验证快照、远端消息和写入结果；网络请求等待不能占住它。当前剪切板状态和待交付队列分开管理，观察成功不等于发布成功。

### 本地观察

1. 获取稳定快照并应用 N(text)。通知可以标记“需重新读取”；若携带快照，必须携带可校验的新鲜度信息，不能把积压旧快照重新当成复制。
2. 同步文本 hash 与当前状态相同则不发布；不同则先更新观察状态，再按队列规则登记发送任务。
3. 系统清空、非文本同样更新观察状态，但不登记发送任务。
4. 每个真实观察到的新本地状态推进本地代次。自身已成功写入对应的通知不算新外部变化。
5. 来源过滤首版不启用；所有普通可观察文本都按这些规则处理。

### 远端接收和写入

1. 解码并过滤自身 origin。
2. 双向后端读取当前实际剪切板，不能只比较过时缓存。若发现此前未处理的本地变化，先按本地观察规则处理。
3. 比较双方 N(text) 的 hash：相同则不调用系统写入；不同才登记/执行写入。
4. 剪切板写入与自身完成登记串行协调。只有确认写入成功，才将预期同步文本的 hash 登记为当前状态，然后处理后续监听通知。
5. 不把写入后读到的任意内容当作自身写入：若实际内容已被外部应用替换，按新的本地状态处理，不能吞掉它。
6. 比较与写入之间仍可能被外部应用抢写。平台后端使用可用的锁/版本核对缩小窗口，不承诺不存在竞态。

### 远程桌面场景

A 复制 X，经远程桌面进入 B，A/B 各发布一次是允许的。两端收到对方消息时当前同步文本已是 X，不再写入。第三个 peer 收到两条 X 时仅需写入一次；远程桌面再次写回同值也不触发上传。

测试不得仅断言最终文本，还要断言有限输入后发布/写入次数停止增长。网络重试导致的重复通知不等于再次传播一次观察到的同值复制。

## 6. 发布队列和网络重试

- 内存 FIFO；网络重连保留，进程退出丢弃，不把剪切板正文写入持久队列。
- 最多 128 条且合计最多 8 MiB，以序列化正文大小计数，包含在途任务的内存占用。
- 每条从本地变化被观察起最多保留 60 秒，等待排队、退避和 HTTP 请求都计入。
- 单次 HTTP 请求最多 10 秒，每条最多 5 次尝试，包含首次；重试退避依次为 1、2、4、8 秒，不超过剩余有效期。
- 同一时刻最多一个发布请求；队首成功、终止或过期后才处理下一条。新复制仍可入队，不能阻塞监听。
- 队列满时丢弃最旧的未开始任务以保留较新的变化，报告原因和数量；已在途请求不声称可撤回。单条超出容量或已无可淘汰任务时，拒绝新任务并报告，不无限驱逐或绕过字节上限。
- 401/403 等权限/配置错误以及不可恢复的 4xx 不盲目重试，明确报告；可恢复连接错误、超时、429、适用的 5xx 在预算内重试。
- 429 尊重 Retry-After；服务器级冷却期对整个发布器生效，不能靠丢弃队首立刻重试下一条来绕过限流。等待超过消息寿命则报告过期。
- 响应丢失时允许重试相同封装，接受服务器偶发重复通知；不生成假成功，不承诺恰好一次，不加 event_id 历史集合。
- 仅以明确成功的 HTTP 响应认定服务器接受了发布；这不是其他 peer 已写入成功的确认。

已观察到的变化按 FIFO 尽力发送，不主动 debounce 合并。即使本地后来变成非文本，先前合法入队任务仍按预算处理，不暗中改成仅保留最新状态策略。

## 7. 接收写入队列和本地重试

- 有界内存 FIFO，默认 128 条 / 8 MiB，以待写文本的 UTF-8 字节计数，包含在途任务，与发送队列分别计数；满时明确报告并丢弃最旧的未开始写入任务。单条超限或无可淘汰任务时拒绝新任务并报告。
- 每条从接收起最多等待 5 秒，最多 5 次写入尝试，每次操作最多 1 秒，退避为 50、100、200、400 ms；每次尝试前重新检查内容、有效期和本地代次。
- 在预算允许且没有新本地变化时，按接收顺序重试暂时占用等可恢复错误。不可恢复错误直接报告；队首失败或过期后继续处理后续消息。
- 已观察到的本地同步文本变化、系统清空或进入非文本状态使更早接收的待写旧任务失效；取消并报告，不让写入重试覆盖已经观察到的本地新内容。其后新到达的消息按正常规则处理。
- 已在执行的操作不能凭取消 Future 假定停止。对外部进程要终止并回收；对原生操作要保证有界执行或完成协调，再核对状态。不能启动并发旧写入，也不能在超时后留下晚到的写入。
- 写入失败不更新为成功 hash；同值 no-op 则属于已满足当前写入目标，不产生系统写入。

只重试本进程已经收到的内容。订阅断线期间没有收到的消息不会自动补齐。

## 8. 配置默认值

所有新增配置在缺省时使用默认值；非法值显式报错，不默默替换。以下是实现时使用的配置接口。

| 环境变量 | 默认值 | 含义 |
| --- | --- | --- |
| SYNC_MODE | receive | receive / bidirectional |
| MAX_MESSAGE_BYTES | 4096 | ntfy 消息正文上限，须与自建实例配置匹配 |
| CLIPBOARD_POLL_MS | 250 | 使用轮询的平台的检查间隔 |
| SEND_QUEUE_MAX_MESSAGES | 128 | 发送队列数量上限 |
| SEND_QUEUE_MAX_BYTES | 8388608 | 发送队列正文总字节上限 |
| SEND_TTL_SECS | 60 | 从观察到变化起的任务寿命 |
| PUBLISH_TIMEOUT_SECS | 10 | 单次 HTTP 超时 |
| PUBLISH_MAX_ATTEMPTS | 5 | 包含首次的尝试次数 |
| PUBLISH_RETRY_BASE_MS | 1000 | 指数退避起点 |
| PUBLISH_RETRY_MAX_MS | 8000 | 指数退避上限；Retry-After 可更长 |
| RECEIVE_QUEUE_MAX_MESSAGES | 128 | 待写队列数量上限 |
| RECEIVE_QUEUE_MAX_BYTES | 8388608 | 待写文本总字节上限 |
| WRITE_TTL_MS | 5000 | 从接收起的写入任务寿命 |
| WRITE_TIMEOUT_MS | 1000 | 单次写入超时 |
| WRITE_MAX_ATTEMPTS | 5 | 包含首次的写入尝试次数 |
| WRITE_RETRY_BASE_MS | 50 | 写入退避起点 |
| WRITE_RETRY_MAX_MS | 400 | 写入退避上限 |

更大的服务端上限不意味着客户端自动获知它，部署时需显式匹配。对某些平台不能表示的文本应明确报错，不做隐式截断或有损编码转换。

## 9. 平台实现方向与验证门槛

以下是实施方向，不是已经通过运行验证的能力声明。

| 平台 | 方向 | 必须验证 |
| --- | --- | --- |
| macOS | NSPasteboard 原生读取，changeCount 轮询；写入可复用命令或使用同一原生后端 | 原生线程约束、访问权限、Unicode/空文本、稳定快照、Screen Sharing 与 UU Remote 回流 |
| Xorg | XFixes CLIPBOARD 变更通知，评估复用 xclip 读写 | 不监听 PRIMARY；空文本、退出状态、后台 selection 生命周期、clipboard manager 接管 |
| KDE Wayland | 在具备 ext/wlr data-control 的版本上监听；优先验证 Rust 协议后端，命令式辅助路线需明确数据帧边界 | 精确检测协议版本、seat、文本 MIME 类型、无焦点访问、生命周期和进程失败 |
| GNOME Wayland | 首版无自动上传，不安装额外扩展 | 明确能力限制；仅保留已能工作的接收路径，不宣称所有 GNOME 版本的命令读写均可用 |

去掉系统私有标记要求不等于所有平台都能可靠报告来源。首版没有通用忽略 PID/app ID 配置。后续先用合成文本调查 Screen Sharing、UU Remote 提供的类型和来源值，不读取或记录用户真实剪切板正文。

## 10. 模块职责与依赖方向

这是涉及状态协调和跨平台边界的 Structural 实施任务；本次仅形成规格。

- 入口/配置：保留当前二进制 n2c 和环境变量入口，选择运行模式，启动及监督各组件。
- 同步状态：N(text)、当前 hash、本地代次、origin、发送/写入队列和状态转移；使用可控时钟及平台接口测试。
- ntfy transport：HTTP 发布、WebSocket 收取、鉴权、应用封装和错误分类；不直接写系统剪切板。
- 平台后端：能力检测、观察通知、稳定快照和有界写入；不直接发布 ntfy 消息。

按职责从 `src/client.rs` 中提取必要模块，平台实现按实际责任分文件；不建立泛用插件框架。新增 HTTP 客户端优先评估 reqwest，SHA-256 使用现成库（如 sha2），origin 使用 UUID 实现；平台绑定和具体版本在能力验证后锁定。Tokio 按需要显式开启 sync/io-util 等特性，TLS 行为与当前平台配置保持兼容。

日志只记录事件类型、平台、队列长度、字节数、尝试次数和失败原因；不记录正文、完整 hash、TOKEN 或完整认证请求。修正现有正文日志、认证请求 Debug 输出和未检查子进程退出码的路径。后台任务失败应能被监督和报告，不能失联后仍显示同步正常。

## 11. 实施顺序

1. **能力验证**：使用合成文本验证 macOS、Xorg、KDE Wayland 的观察/写入和同值判断；验证自建官方服务的三订阅者广播、tag 转发、封装保真、大小限制。GNOME 只验证能力报告与可用接收。固定实际版本和依赖。
2. **同步核心**：先完成 N(text)、协议编解码、hash/origin、稳定快照协调、FIFO 及预算；用小型假后端和可控时钟测试行为，不绑定第三方内部实现。
3. **双向 transport**：复用订阅语义，新增发布、错误分类和全局限流等待；分离连接重建与观察状态，处理关闭连接、流结束和后台任务失败。
4. **平台接入**：依次接入 macOS、Xorg、KDE Wayland；维持仅接收兼容路径，不因缺少上传组件破坏原有可用写入。
5. **端到端验证与文档**：测试三 peer、远程桌面及失败场景，补充配置、平台依赖和实际验证矩阵。移除正文/凭据日志，不顺带修复无关问题。

本次不创建实现提交、不部署服务、不更改系统剪切板。实现任务可随后从本规格拆为 `.scratch/clipboard-sync/issues/NN-<slug>.md`，每个任务独立成文件。

## 12. 验收矩阵

- 文本：尾部 CR/LF 全去除，开头和中间空白保留；N(N(x)) = N(x)；中文、emoji、空字符串；大小边界按 JSON 转义后的字节计算；不可表示文本报错不截断。
- 本地：启动不发布基线；重复文本或仅改变尾部换行不上传；X→Y→X 正常；非文本/清空后再次复制 X 能上传；读取失败不产生空文本或清空事件。
- 网络：自身 origin 的延迟 X 不覆盖本地 Y；普通 ntfy 文本正常；保留 tag 下的坏 JSON/未知版本被拒绝；WebSocket 回送先于 HTTP 响应仍正确；不自动重放历史。
- 发布：用假时钟验证次数、退避、总寿命、容量和字节预算；401/403 不盲重试；429 全局冷却；响应未知时允许重复通知；重连保留队列、进程重启不恢复。
- 写入：暂时占用后成功；失败不登记 hash；过期队首不阻塞后续；新本地变化取消旧待写任务；超时回收；外部抢写及积压旧快照不被假记为自身写入。
- 三 peer：无重试和远程桌面时 A 复制一次，B/C 均得到同步文本，A 回送零写入；持续多个观察周期后发布次数仍为 1。
- 远程桌面：A/B 可各发布一次同值，互收零冗余写入，C 只写一次；验证 ntfy/远程桌面先后顺序互换、无私有标记、尾部换行差异。记录延迟旧值及中间换行变换行为，不伪造全面无回流保证。
- 平台：各支持平台的真实桌面 smoke test；GNOME/无协议环境必须报告自动上传不可用。交叉编译不能代替桌面运行验证，未测平台明确标记。
- 实施验证：受影响目标的 cargo fmt、cargo check、cargo clippy、cargo test，以及三客户端集成测试；只有文档变更时检查格式、引用和决定一致性，不声称 Rust 功能已验证。

## 13. 已接受的边界

- 系统剪切板不是历史队列，轮询/事件后读取可能漏掉已被覆盖的中间状态；“已观察”不等于捕获每次系统写入。
- hash + origin 抑制同值传播和自身回送，不能识别来源已丢失的旧值。A 已复制 Y，B 经远程桌面延迟发布旧 X，仍可能使 A 回到 X。
- 有界重试可能重复交付；若两次 X 之间夹杂 Y，第二次 X 不一定是 no-op。不维护消息历史，不能保证恰好一次或全局最终一致。
- 本地代次只保护重试期间已经观察到的新复制，不能阻止不可见的并发抢写，也不建立跨设备时间顺序。
- 来源元数据过滤尚未验证；远程桌面若持续回流不同状态，可靠的操作性解决办法是关闭其剪切板转发，只保留本项目通道。
- 队列满、超时、过期、进程退出都会导致未同步内容；通过明确状态与日志报告，不将“尽力交付”表述为保证送达。
