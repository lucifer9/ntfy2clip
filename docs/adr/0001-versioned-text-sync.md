# 用版本化应用消息传输剪切板文本

ntfy 的普通文本发布会去除首尾空白，仅改用 ntfy 的 JSON 发布 API 不能解决。项目选择所有 peer 一起升级：用带 origin 的版本化应用 JSON 封装承载同步文本，并以保留的 ntfy tag 识别协议；新版仍接收普通 ntfy 文本，但不承诺旧版二进制能解读新版同步消息。

考虑过维持纯文本正文、仅通过 tags 携带 origin，以便旧二进制透明接收。放弃该方案是因为服务端对正文的变换无法满足已确定的文本语义。末尾 CR/LF 的删除是用户明确选择的客户端规则，与服务端无差别裁剪其他首尾空白不同。

协议字段、文本规则和错误处理以 [正式规格](../../.scratch/clipboard-sync/spec.md) 为准。后续协议变更须考虑已部署 peer 的升级与兼容成本，不能把封装当成任意可改的内部格式。
